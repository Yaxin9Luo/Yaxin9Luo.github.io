我们让一个 AI agent 一轮接一轮地改写另一个 agent 的 harness。每次修改，只有分数提升越过一条按实测噪声设定的门槛，才会被保留。最后，我们换上一个更严格的评分器，给同一批页面重新打分。**每个 harness 测得的提升都缩水了三分之一到 70%**。最好的那个缩水约一半：+0.176（90% 区间 +0.12 到 +0.23）变成了 +0.086（+0.02 到 +0.15）。页面一个字没改，变的只是裁判。[^rerun]

哪个数字是对的？我们判断不了，而这正是结论：在这么小的差距上，两个评分器都没有经过验证。在开放式任务上，“harness 到底提升了多少”这个问题，脱离评分器就没有答案。

这不只关乎网页。如果你的团队靠 AI 裁判的分数来挑 prompt、skill 或工作流，同样的效应都会出现：按品牌细则打分的营销文案，按质检清单打分的客服回复，按病历书写规范打分的临床记录。你测到的提升有一部分属于裁判，小幅提升大多是噪声，而你给优化器看的任何评分细则，都会被它抄走。

## 换一个评分器，提升缩水三分之一到 70%

最后，我们从四条优化谱系（每种反馈设置一条）各取第一个被保留的版本，把它们在 held-out 任务上的页面评了两遍：一遍用优化时用的宽松评分器，一遍用取代它的严格评分器。在同一个门控前指标上，每个提升都缩水了：

- 只看结果的，缩水 33%；
- 看失败评分项的，缩水 70%；
- 两个看完整反馈的，缩水约一半。

把门控扣分算进去，排名也变了。在严格评分器下，只看结果的 harness 排第一，+0.090，而最好的完整反馈 harness 是 +0.070。它并没有做出更好的页面：起始 harness 在 16 次运行里有 4 次被门控扣分，而只看结果的 harness 一次也没有。

![一个任务，两个评分器](/blog/harness-optimization/figs/example-page.png "一个 dev 任务：左边是起始 harness 做的页面，右边是一个被保留的 harness 做的页面。和宽松评分器相比，严格评分器给起始页面打得更高（0.74 对 0.70），给保留页面打得更低（0.88 对 0.99）。保留页面的领先从 0.30 变成了 0.14。")

那到底哪个评分器对？我们拿评分器的一个早期版本，和一个按书面规程打标的独立 AI 标注者做了对比；我们没有人类一致性数据。在差别明显的页面对上，两者 6 次全部一致。在差别细微的页面对上，32 次里只有 16 次一致，等于抛硬币，不过样本不大。这项研究在 held-out 任务上的提升在 0.03 到 0.18 之间，看起来正落在这个“细微差别”区间，而我们测过的评分器在这里都没有得到验证。可以在下面自己探索。看过失败评分项的 harness 做出的页面，在严格评分器下掉分最多。

```embed
{"src": "/blog/harness-optimization/interactive/rq1.html", "height": 520, "autosize": true, "title": "哪个评分器是对的？", "caption": "左：评分器早期版本与按规程打标的 AI 标签在页面对上的一致率，按页面差别大小分组（90% 区间）。右：每个 held-out 页面在两个评分器下的分数；72 个里有 56 个落在对角线下方。图中文字为英文。"}
```

宽松评分器在高分段还饱和了：它把 31 个强页面里的 12 个打到了 0.9 以上，而一个参照 AI 裁判只给了 5 个。

我的结论是：**脱离评分器的提升，不算结果。** 每个提升都至少报告两个评分器下的数字；评分器一变，就把选定的检查点重新评一遍。我们换了九个评分器版本才学到这一点，每次修复都解决一个问题，又暴露出另一个：

- 第一个评分器不管页面做了什么，100 条裁判断言里都会放过 60 条。
- 后来的版本会因为 4–5 px 的溢出，把正确的页面打成零分。
- 把这两个问题都修好的版本，又在高分段饱和了。

## 运行之间的噪声，和你的保留门槛一样大

同一个 harness 在同一个任务上跑两次，分数的标准差就有 0.05 到 0.07。同一个页面重新评分，只会变动约 0.02。所以大部分噪声来自 agent 的运行，而不是评分器。

保留规则在六个 dev 任务上取平均，这有帮助，但不够。我们 0.0514 的门槛，只比六任务比较的噪声高出约 1.6 个标准差。用这些数字搭一个简单模型：

- 一个在每个任务上都真实提升 0.05 的修改，只有约一半的概率被保留；
- 一个毫无作用的修改，有约 7% 的概率被保留。

我们也想过取巧。我们把门槛挪到 logit 尺度上（这在分数接近上限时更公平），并把成本和不稳定的运行也计入。然后，用新规则重新裁决原规则回退掉的 12 个修改。在宽松评分器下，新规则会保留其中 4 个；在严格评分器下，一个都**不**保留。在我们的数据里，选择规则没法脱离它所读的评分器单独调好。

## 给优化器看失败的评分项，它就会抄

想象一个考前看到评分表的学生：没过多久，他的笔记读起来就像那张评分表。看失败评分项或完整反馈的 Meta Agent 从来没看到过完整的评分细则，只看到页面没通过的那几条的原文。它们在 dev 上拿到了最大的提升。然后我们去读了它们的 diff：

- 这两种设置下被保留的 9 个版本里，**8 个**的 harness 里有评分细则的文字，要么是条目编号，要么是几乎逐字照搬的句子。我们的统计只是下限。
- 在它们的全部候选里，37 个中有 29 个这样做。
- 只看结果的 11 个候选，一个都没有。

在 held-out 任务上，喂过评分细则的 harness 并没有比只看结果的 harness 表现出可靠的优势，而严格评分器给它们页面扣分最多。

优化器自己的笔记，说明了它在做什么。在第二阶段，控制循环谱系第一个被保留的修改，以这样一条假设开头（可以在下面的记录里读到）：*“Make one verification pass catch what the grader checks.”*（让一次自检就抓住评分器检查的所有东西。）这不是优化器的 bug，而是它对自己看到的东西做出的理性反应。**反馈可见性就是信息泄露**，应该按信息泄露来对待。

![反馈级别与提升](/blog/harness-optimization/figs/fig-rq3.png "只要反馈里出现失败的评分项，就会出现抄评分细则的现象。dev 上更大的提升没有延续下去：在严格评分器下的 held-out 任务上，各反馈级别分不出高下。")

## Reward hacking 确实发生了，只是不以作弊的形式

我们为硬作弊设了两个陷阱：

- 一个门控：任何对裁判喊话的页面直接记零分；
- 一个 **canary**：一个任何需求都没提到的、预埋的计分漏洞。

canary 是会被触发的：它在 354 次 dev 运行里出现了 6 次，其中 2 次来自未经修改的起始 harness，所以单次命中说明不了什么。但在严格评分器下，没有一个 held-out 页面钻了它（174 个里 0 个）。注入门控在 473 次 search 和 dev 运行里一次都没触发。我们没有埋一个已知的注入来测试它，所以这个零应读作“没有观察到”，而不是“不可能”。

但 reward hacking 还是发生了，以**拟合评分器**的形式：

- harness 把评分细则的原文抄进了自己的指令；
- 48 个候选里有 11 个，把具体任务的事实和选择器写死在了 harness 里；
- 它们揣摩裁判能看到什么。有个 Meta Agent 的笔记，专门围绕“评分器那张从不滚动的整页截图”做计划。

这些做法都能通过检查，却没有检查本来想要的那种品质。

这里有一个让人不太舒服的转折：判断一个修改是 hacking 还是真本事，本身也需要一个评分器。写进 harness 的对比度检查，如果读者在乎对比度，就是本事；如果只有这个评分器在乎，就是 hacking。在这项研究里，在 harness 搜索这个强度的优化压力下，评分器的盲区和校准误差对结果的影响远大于作弊。我们预计，随着优化压力增大，作弊风险也会上升。

## 几乎所有提升都来自第一次修改

**11 个**被接受的改进里有 **9 个**是直接在起始 harness 上做的修改，其中 8 个出现在第一轮迭代。之后，大多数谱系就停滞了。只有一条完整反馈谱系又保留了第二步。控制循环谱系在第二阶段又提升了一次：门控前 +0.043，算上门控后与零无法区分。被保留版本的子版本，在 24 次尝试里平均只比父版本高 +0.009；而 dev 上最好的候选，在 held-out 任务上并不比它们的父版本强。

不过，第一次修改是实打实的。在 dev 上，看失败评分项或完整反馈的版本，胜过“让评分器从起始 harness 的 8 次运行里挑最好的一次”；只看结果的版本没有越过这条线。而且一个最终的 harness 每个任务的成本只是这种重采样的一小部分，两到四个任务就能回本。

为什么会停滞？最显眼的嫌疑是评分器饱和，但它解释不了：换成严格评分器重新裁决，被回退的候选没有一个会变成保留。我的猜测是，一个强模型配上一个还不错的 harness，有一部分容易拿到的提升空间，一次认真的修改就能拿走。之后的提升，就小于这个评分器和保留规则能分辨的程度了。更强的优化器或更大的预算，也许能找到更多。

| 假设和 diff 里直接点名评分器的检查项 | 给每个候选标注是否抄了评分细则、是否写死了具体任务的细节 |

## 如果有人告诉你，他们的 agent 会自我改进

向他们要三样东西：

1. **换一个评分器重评的结果。** 换了裁判提升就减半，说明提升有一部分来自裁判。
2. **第一次修改之后的 held-out 曲线。** 如果后来的修改只在被挑选时用的任务上占优，这个循环就是在拟合噪声。
3. **diff。** 抄评分细则、写死任务细节，在分数里看不出来，在文本里一目了然。

## 给搭建这种循环的人的建议

1. **每个数字都注明评分器。** 报告两个评分器下的提升；评分器一变，就把选定的检查点重新评一遍。
2. **用干净的运行间噪声来设保留门槛**，在第一个候选之前测好，然后冻结。
3. **把反馈当作泄露。** 你给优化器看的评分细则，往往会出现在 harness 里。
4. **读 diff。** 拟合评分器在分数里看不出来，在文本里一目了然。
5. **把可观测性上的缺口当作评分器的 bug。** 裁判看不到的，优化器就会学会利用。
6. **预期第一次修改就占了大头**，把剩下的预算花在评分器上。

在 dev 上，一次好的修改胜过暴力重采样，而且跑起来很便宜。在我们的研究里，限制开放式任务上 harness 优化的，既不是优化器的聪明程度，也不是它是否诚实，而是评分器。先把评分器做好。
